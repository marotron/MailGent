Option B: three trust classes

Same Mac can host strong and weak local agents. Remote agents stay in a third class that can never receive private scopes — even if the user tries to grant them.

2. What “private scope” means

Private scopes are mailbox regions you treat as especially sensitive. Exact list is decided later in this ticket; examples below show the idea.

Example scope local-trusted local-untrusted remote

Personal bank / medical / family labels Grantable Blocked by class Blocked by class

3. Option A vs Option B

A — Two classes

Only local and remote.

  • Any paired local agent can be given private scopes.
  • Simpler mental model and UI.
  • Risk: a throwaway local script gets the same ceiling as Cursor.

B — Three classes

local-trusted, local-untrusted, remote.

  • Local is split: trusted vs cautious guest.
  • Private scopes reserved for agents you explicitly elevate.
  • Cost: one more choice at pairing / in agent settings.

4. Concrete stories

Trusted

Daily coding agent on this Mac

You pair Cursor over UDS, mark it local-trusted, and grant work mail plus a private “family” smart folder. It reconnects without re-pairing. Private grant is legal because the class ceiling allows it.

Untrusted

Trying a new local MCP client

You pair an unknown CLI. MailGent defaults it to local-untrusted. You can grant “newsletter@… last 7 days, subject+snippet only.” If you try to attach the private family folder, MailGent refuses: class ceiling, not a missing grant checkbox.

Remote

Cloud agent for one afternoon

You open a 1-hour remote session. The agent can only receive non-private grants you already allow for remote. Even if UI showed a private folder toggle, saving it would fail closed. Session ends → reachability ends.

Promotion

Promoting untrusted → trusted

After the CLI proves useful, you elevate it in MailGent (extra confirmation / Touch ID). Only then can private scopes be attached. Demotion or revoke immediately drops private grants and kills sessions.

5. Decision flow at pairing

  1. Agent connects (UDS preferred, or hardened loopback HTTP).
  2. MailGent shows pairing challenge — not yet trusted.
  3. You approve pairing and choose class:
    • local-trusted — full local ceiling, private scopes allowed later
    • local-untrusted — local guest ceiling, private scopes impossible
    • If the connection arrived via remote relay → class is forced to remote
  4. Separately, you attach concrete grants (accounts, folders, dates, fields).
  5. Deny-by-default: anything not granted is invisible / refused.

6. Why B exists

Topology already proved “local vs remote.” Option B answers a different fear: not every process on my Mac deserves the same mailbox ceiling. It does not replace grants, approvals, audit, or revocation — it only caps what those systems are allowed to offer.

Tradeoff to decide: is the extra pairing choice worth preventing a careless private grant to a throwaway local tool? If yes → B. If you would almost always mark local agents trusted anyway → A is enough for v1.
