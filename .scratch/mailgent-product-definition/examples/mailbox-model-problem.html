MailGent product grilling Ticket 05 · Canonical mailbox model

Same email. Two provider worlds.

MailGent needs one shared way to talk about accounts, messages, drafts, and search — without pretending Gmail labels and Yahoo folders work the same. Below are concrete examples of where the models collide.

1. One message, two placement rules

Imagine the same invoice arrives in a Gmail account and a Yahoo account. Where does it “live”?

Gmail · labels (many-to-many)
Invoice #4412 — Acme Corp
from: billing@acme.com · id: 18c2…
INBOX Finance Vendors/Acme UNREAD

One message can wear several labels at once. Removing INBOX does not delete the message; it can still be under Finance and Vendors/Acme.

Honest model Message has a set of labels.
Yahoo · folders (usually one place)
Invoice #4412 — Acme Corp
from: billing@acme.com · uid: 90211
Inbox \Seen = false
Inbox
  └─ Invoice #4412 ← lives here
Finance
Vendors
  └─ Acme

Moving it to Finance typically removes it from Inbox. It is not simultaneously in both places the way a Gmail label set is.

Honest model Message has a primary folder (plus SPECIAL-USE roles like Sent/Drafts).
Bad abstraction: “everything is a folder” If MailGent forces Gmail into exclusive folders, “also keep Finance + Vendors/Acme” becomes impossible or fake. If it forces Yahoo into multi-label semantics, “move to Finance” becomes ambiguous (copy? tag? leave Inbox?).

2. “Archive” means different operations

Users and agents both say “archive this.” Providers implement that differently.

User intent Gmail reality Yahoo reality
Archive invoice Remove INBOX label; message remains with other labels / All Mail Move message into an Archive / All Mail style folder (SPECIAL-USE if present)
Still find it under Finance? Yes, if Finance label remains Only if it was moved/copied into a Finance folder — usually no longer in Inbox
Agent tool if naively named archive() Must map to label mutation Must map to folder MOVE

3. Unified search must not invent a mega-mailbox

You connect alex@gmail.com and alex@yahoo.com, then search invoice acme. Results should feel unified, but each hit still belongs to one account and one placement model.

Unified search · query: invoice acme
Gmail
Invoice #4412 — Acme Corp
labels: INBOX, Finance, Vendors/Acme
unread
Yahoo
Invoice #4412 — Acme Corp
folder: Inbox
unread
Gmail
Re: Invoice #4412 — paid
thread with previous Gmail message · labels: Finance
read
Good unified view Ranked merge of per-account hits. Every row shows source account + provider placement.
Bad unified view Pretend both invoices are one thread, or one shared “Finance folder” across providers.

4. Threads do not cross accounts

Gmail has first-class threads. Yahoo may expose conversation/thread ids via IMAP extensions. Neither means MailGent should glue two provider inboxes into one conversation object.

1

Work reply on Gmail

You discuss a contract on alex@gmail.com. Gmail groups 6 messages as one thread.

2

Same person mails your Yahoo

They accidentally send the next reply to alex@yahoo.com. Subject looks related.

3

Product rule for v1

MailGent may show them near each other in search results, but must not invent a cross-account thread id. Agents must not “reply in thread” across providers.

5. Drafts are owned by one account

An agent drafts “Thanks, payment sent.” That draft must live somewhere concrete.

Choice What happens Verdict for companion v1
Draft on Gmail account Stored as Gmail draft (labels/Drafts); send uses Gmail identity Valid — account-owned
Draft on Yahoo account Stored in Yahoo Drafts folder; send uses Yahoo identity Valid — account-owned
“Floating” draft with no account Looks convenient until send time: which From? which Sent folder? Reject for v1
Why this matters for agents Mutation approval (“allow send”) is meaningless unless the draft already names the owning account and From identity.

6. What breaks if MailGent lies

Policy / smart folder: “Finance mail”

User grants an agent access to Finance.

  • Gmail: messages with label Finance (even if not in Inbox)
  • Yahoo: messages currently in folder Finance
Same policy name, different membership rules The grant UI must explain that, or users will think Yahoo Inbox mail tagged mentally as “finance” is included when it is not.

Agent action: “remove from Inbox”

  • Gmail: strip INBOX label
  • Yahoo: MOVE out of Inbox into another folder — destination required
One tool, two semantics Without provider-specific facts on the canonical message, the agent API either fails closed or does the wrong thing.

7. The decision this ticket must lock

Not “which database tables,” but the product nouns humans and agents share.

Shared noun Same across providers? Provider-specific fact that must remain visible
Account Yes — one login Provider = Gmail or Yahoo
Identity (From) Yes — belongs to an account Send-as aliases differ by provider
Message Yes — atomic email Provider ids, flags, attachment handling
Thread Only within one account Gmail thread id; Yahoo thread/OBJECTID when available
Location No single metaphor Gmail: label set · Yahoo: primary folder
Draft / Sent Yes — account-owned Provider draft/sent locations
Search hit Yes — always sourced Account + labels or folder on every result
Recommended product stance Canonical shared objects for account, identity, message, thread, draft, and search — plus honest provider placement (labels vs folder). Unified and separate views are filters over the same objects. No cross-account threads. No accountless drafts.
